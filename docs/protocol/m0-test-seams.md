# M0 contract-test seams

## Purpose

This note defines the contract tests for [Issue #2](https://github.com/RockyRous/Orbita/issues/2): prove one pinned root-task round trip without choosing a production framework, storage engine, process topology, or execution-status model.

The tests use exactly two approved seams:

1. the public Codex App Server process boundary over newline-delimited JSON on stdio; and
2. the deterministic normalized probe-output/fixture boundary.

No test reaches through either seam to private Codex storage, terminal presentation, probe helpers, internal queues, or implementation-specific classes. This follows [ADR 0001](../adr/0001-app-server-boundary.md), the source hierarchy in [compatibility.md](compatibility.md), and Gates A and B of the [spike plan](spike-plan.md).

## Contract sources

Expected behavior comes from independent sources, in this order:

1. the exact local binary reported by the run (`codex-cli 0.170.0` at design time);
2. schemas generated by that binary, with stable and experimental generation kept distinct;
3. the official OpenAI [0.170.0 App Server source tag](https://github.com/openai/codex/tree/rust-v0.170.0/codex-rs/app-server) and [protocol source](https://github.com/openai/codex/tree/rust-v0.170.0/codex-rs/app-server-protocol);
4. the official [Codex App Server integration instructions](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server), which specify newline-delimited stdio, `initialize` followed by `initialized`, `thread/start`, `turn/start`, streamed notifications, and `turn/completed` as the terminal signal.

The generated schema is a validation oracle, not a golden output. A test must not copy values emitted by the implementation under test into its expected value. Small expected manifests and normalized fixtures are hand-authored from the sources above and reviewed as specifications. Regenerating a snapshot is never sufficient to approve a change.

All claims remain pinned to the recorded executable digest, reported version, feature configuration, generated-contract digest, transport, and probe-input revision. A result from `main`, `latest`, or another installed binary cannot silently update the 0.170.0 expectation.

## Seam 1: public process boundary

### Boundary

Launch the pinned `codex app-server --listen stdio://` executable as a child process in a disposable Git repository and isolated probe home. Write one JSON message per stdin line and read one JSON message per stdout line. Treat stderr only as a separately sanitized diagnostic channel.

The test observes only:

- process startup, exit, and a bounded deadline;
- JSON request/response correlation at stdout;
- public responses, server requests, and notifications;
- the generated schema for the recorded stable or experimental profile.

It does not import probe modules or inspect files created by Codex. This catches transport, handshake, schema, correlation, and terminal-outcome regressions; it does not prove projection, persistence, recovery, UI behavior, or compatibility with any other runtime.

### Minimal red-green slices

Implement these slices in order. Each slice is one failing test followed by only enough implementation to make it pass.

#### P1 — initialized public connection

Given the pinned executable, fixed client metadata, recorded feature overrides, stdio transport, and an isolated disposable environment:

1. send an `initialize` request with a fixed request ID;
2. require a successful response with the same ID whose result validates against the generated `InitializeResponse` schema for the selected profile;
3. send the `initialized` notification; and
4. prove the connection remains usable by obtaining a schema-valid response to the next Issue #2 request (`thread/start`).

Independent expected values are the literal method names, fixed client metadata, fixed request IDs, selected profile, and the fact that a response is successful and correlated. Do not assert the entire initialize or thread payload, object key order, incidental notifications, timestamps, paths, default model, or fields not required by the pinned schema.

This is red if the executable cannot start, stdout contains a non-JSON protocol line, the request deadline expires, the response ID differs, an error envelope is returned, schema validation fails, or the connection is unusable after `initialized`.

#### P2 — one correlated root turn reaches an authoritative outcome

Continue from P1's public connection:

1. take the non-empty thread ID only from the successful `thread/start` response;
2. call `turn/start` with that thread ID and the fixed synthetic prompt `Reply with exactly ORBITA_M0_OK and do not use tools.`;
3. take the non-empty turn ID only from the successful `turn/start` response;
4. observe at least one documented, schema-valid streaming notification correlated to that thread/turn; and
5. wait for a schema-valid `turn/completed` whose thread and turn IDs equal the IDs returned above.

The hand-authored expected outcome is:

```json
{
  "rootThreadObserved": true,
  "turnObserved": true,
  "streamingEvidenceObserved": true,
  "terminalSignal": "turn/completed",
  "terminalStatus": "completed",
  "finalAgentText": "ORBITA_M0_OK"
}
```

Only `turn.status == "completed"` is success. A failed or interrupted turn, process exit, EOF, silence, idle-looking thread, or final text without the matching `turn/completed` is not completion. The official integration instructions explicitly distinguish `completed`, `failed`, and `interrupted`.

Assert causal relationships, not a total event sequence: responses may interleave with notifications, and additional schema-valid notifications are allowed. Preserve their observed order in the captured transcript. Do not assert generated identifier formats, event counts beyond the required evidence, token usage, timing, item IDs, reasoning content, or the full final turn object.

#### P3 — process-boundary failures cannot become success

Use three narrow negative cases:

- A `turn/start` using a known-invalid thread ID must yield a correlated public error or a documented terminal failure; it must not yield a successful normalized outcome.
- EOF/process exit or deadline expiry before the matching `turn/completed` must yield a failed probe result with the last observed protocol evidence; it must never synthesize terminal success.
- A stdout line that is not a JSON object, or a required response/notification that fails its pinned schema, must fail that run and preserve only a sanitized diagnostic description.

Do not assert human-readable error text, private error causes, a particular process exit code, or undocumented error data. If the pinned generated contract provides a stable machine-readable error code for the exercised case, assert that code; otherwise assert only the error envelope and absence of success.

P3 is part of the Issue #2 harness safety net, not a claim that every App Server error mode has been tested.

## Seam 2: normalized output and fixture boundary

### Boundary

Feed a finite captured protocol transcript plus its run metadata into the public normalization entry point and observe one normalized result. The test uses checked-in, hand-reviewed input fixtures; it never launches App Server. The same input is replayable on every machine.

This catches nondeterministic normalization, broken correlation, unsafe fixture production, accidental reliance on object-key order, and digest drift. It does not prove that the live runtime emits the fixture; P1 and P2 own that proof.

### Minimal red-green slices

#### F1 — a known transcript produces a literal normalized result

Start with the smallest transcript containing successful initialization, `thread/start`, `turn/start`, one correlated streaming event, and matching `turn/completed`. Include unrelated, schema-valid noise so the test proves correlation rather than "last event wins" behavior.

Compare the result to a small literal manifest authored independently from the normalizer. It must contain:

- recorded runtime/version/executable identity and feature profile;
- `stdio` transport and generated-contract digest;
- stable/experimental classification for every surface actually used;
- deterministic aliases for the observed thread, turn, and relevant item IDs;
- the six expected outcome fields from P2;
- evidence references that point to the normalized transcript entries supporting each outcome field; and
- an explicit failure/unknown value for any required fact not present in the input.

Do not golden-test the normalizer's private data structures, helper names, intermediate representation, file layout, or serialization library.

#### F2 — replay is byte-stable and equivalent clean runs agree

Run normalization twice on the same fixture in fresh processes. Canonically serialize the normalized artifact as UTF-8 JSON with sorted object keys, preserved array order, no insignificant whitespace, and one trailing newline. The bytes and SHA-256 digest must be identical.

Then normalize a second hand-authored fixture representing an equivalent clean run with different raw IDs, timestamps, request IDs, disposable paths, and harmless additional notifications. Compare its **repeatability projection**, not its entire transcript, to the first run.

The repeatability projection contains only:

```text
runtime identity + feature profile + transport
generated stable/experimental contract digests and classifications
root/turn correlation facts
required evidence kinds (as a sorted set)
terminal method + terminal status + exact sentinel text
```

Canonicalize this projection by the same JSON rule and record its SHA-256 as the repeatability digest. Equivalent clean runs must have the same repeatability digest. Each full sanitized fixture has its own content digest and may legitimately differ because its evidence order and additional events are retained.

The expected repeatability projection and, once reviewed, its literal digest live in the test data. The test must not call the production normalizer to manufacture its expected file or expected digest.

#### F3 — incomplete or unsafe input fails closed

Add one negative example at a time:

- missing matching `turn/completed` produces a non-success result with an explicit missing-terminal reason;
- a terminal event for another turn does not complete the selected turn;
- conflicting reuse of an observed source ID fails normalization instead of merging two executions;
- an unknown notification is retained in bounded sanitized diagnostic evidence and does not alter the known turn outcome; and
- a seeded credential or forbidden private path surviving sanitation prevents fixture emission.

The last two cases exercise only the fixture boundary needed by Issue #2. They do not claim Gate F's full unknown-variant projection behavior or Gate G's complete retention/redaction policy.

## Fixture sanitation

Sanitize before any raw protocol data is written to a checked-in fixture. Unsanitized capture may exist only in the disposable run directory and must be removed after normalization whether the run succeeds or fails.

Apply these rules in order:

1. Validate each protocol message against the generated contract selected by the recorded profile. Keep invalid input only as an in-memory diagnostic until a sanitized summary is produced.
2. Remove known authentication, token, cookie, credential, authorization-header, and environment-value fields by case-insensitive key policy. Redact seeded secret values wherever they occur, including free text.
3. Allowlist content needed by this experiment. Preserve the synthetic prompt and `ORBITA_M0_OK`; omit unrelated prompt, reasoning, source, command, tool-output, and model-response content.
4. Replace absolute probe-home, disposable-repository, user-home, username, and platform-specific temporary paths with typed placeholders. Normalize separators only inside recognized path values, never arbitrary text.
5. Replace runtime-generated identities by first causal definition, then reuse the same alias for every reference: `<THREAD_1>`, `<TURN_1>`, `<ITEM_1>`, and so on. Never allocate aliases from object-key iteration order.
6. Replace or omit wall-clock timestamps, durations, request IDs, token counts, and other volatile values unless they are required evidence. Preserve relative message order; do not sort the transcript.
7. Canonically serialize only after sanitation. Run a second forbidden-pattern scan over both keys and string values. Fail closed if a seeded secret, credential-shaped field, real private path, or username remains.

Stdout protocol evidence and stderr diagnostics remain separate. Stderr must never be parsed as protocol, and its sanitized digest must not affect protocol repeatability. A fixture records which fields were removed or aliased as sanitation metadata without retaining their original values.

These rules implement the pre-persistence and normalization intent in [diagnostics-and-data.md](../security/diagnostics-and-data.md). The stricter user-export pass remains outside Issue #2.

## Digest strategy

Record algorithms and inputs, not only hex strings:

- **Executable digest:** SHA-256 of the exact executable bytes selected for the run.
- **Contract digest:** SHA-256 over a canonical manifest of relative schema path plus each schema file's SHA-256, separately for stable and experimental generation. File timestamps and absolute paths are excluded.
- **Full fixture digest:** SHA-256 of the canonical sanitized normalized artifact. This identifies one evidence capture.
- **Repeatability digest:** SHA-256 of the canonical repeatability projection defined in F2. This answers whether two clean runs are observably equivalent for Issue #2.

The run manifest also records the CLI-reported version, exact generation commands and flags, feature overrides, transport, operating system, probe-input revision, schema profile used for each message, and sanitation-policy version. A digest match without matching context is not a compatibility result.

## Deliberately not tested here

Issue #2 does not test:

- follow-up turns, interrupt, approvals, delegation, child correlation, recovery, pagination, reconnect, or background continuation;
- production projection, durable storage, bounded-buffer limits, export, clear-data behavior, or status mapping;
- UI flows, attention state, root-task Finish/Archive lifecycle, or roadmap claims;
- websocket, daemon, proxy, TCP, or embedded transports;
- private Codex storage, terminal rendering, proprietary desktop behavior, or internal Rust/Python/TypeScript APIs;
- every schema method, experimental feature, model/provider, sandbox, operating system, or App Server version;
- exact notification ordering beyond causal correlation, performance, token usage, or model quality; or
- full Gate F idempotency/migration behavior and Gate G retention/sensitivity measurement.

Passing these tests proves only the recorded Issue #2 round trip for the pinned runtime and configuration. It does not change the current "no supported version" statement in [compatibility.md](compatibility.md).

## Builder handoff

After the probe code exists, the builder should:

1. expose one process-level test command that accepts the executable path, isolated home, disposable project, fixed feature profile, and bounded deadlines;
2. expose one pure normalization command or API that accepts transcript plus run metadata and emits canonical sanitized output;
3. implement P1, then P2, then P3 as separate red-green slices; implement F1, then F2, then F3 the same way;
4. keep live tests explicitly marked because they require a pinned binary, authentication/model access, and network; keep fixture tests offline and mandatory;
5. save a sanitized failure artifact on live failure, but never overwrite an approved fixture automatically;
6. print the four digests and manifest location on success; and
7. submit fixture or expected-value changes for human review with the generating runtime/configuration and source justification.

Before Issue #2 can close, run the fixture suite twice from clean processes, run the live slice twice from clean isolated environments, compare repeatability digests, validate every fixture against the recorded generated schema/profile, scan for forbidden content, and include the commands and results in the issue evidence.

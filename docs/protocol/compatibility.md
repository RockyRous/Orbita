# App Server Compatibility

## Status

No Codex App Server version is supported yet. M0 must validate a pinned local runtime before Orbita makes product promises.

The development environment exposed `codex-cli 0.170.0` during product discovery, but that observation is not a compatibility claim and does not replace a reproducible M0 run.

## Sources of truth

Use, in order:

1. the exact local `codex` binary used by the experiment;
2. schema or TypeScript bindings generated by that binary;
3. captured and sanitized request, response, and notification fixtures;
4. the official [App Server documentation](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md) and [Codex source](https://github.com/openai/codex);
5. prose in Orbita only as a record of tested results.

The official open-source boundary includes the Codex CLI, App Server, and SDK. The official desktop UI is not the implementation base for Orbita. See [ADR 0001](../adr/0001-app-server-boundary.md).

## Contract acquisition

The installed CLI currently exposes commands for generating JSON Schema and TypeScript bindings. M0 must record the exact command, version, flags, output digest, and feature configuration used. Experimental fields are kept separate from stable support claims.

Do not maintain a handwritten list of guessed method names or payloads in product documentation.

## Compatibility policy

- Pin every fixture and capability result to a runtime version and feature configuration.
- Treat stable, experimental, deprecated, and unavailable surfaces separately.
- Validate incoming messages before projecting them.
- Preserve unknown variants in the bounded diagnostic buffer.
- Let an unknown variant degrade only the affected projection, not the entire task workspace.
- Never infer completion from silence, transport closure, or a missing indicator.
- Prefer a weaker source-backed card over a richer reconstruction.
- Detect an unsupported runtime before starting a root task when possible.

## Capability matrix

M0 owns the first populated version of this table.

| Capability | Required product behavior | Evidence required | Result |
| --- | --- | --- | --- |
| Initialize a client | Establish a compatible session | Successful pinned request/response | Directly observed |
| Start a root task | Create one thread and turn | IDs plus live events and terminal outcome | Directly observed |
| Follow up | Add a turn to the same root task | Same thread identity and new outcome | Untested |
| Interrupt | Stop the current root turn | Supported action and confirmed outcome | Untested |
| Discover delegation | Show observed delegated work | Direct event or item evidence | Untested |
| Correlate a child | Create a task card or fallback | Stable or safely correlatable identity | Untested |
| Relate parent and child | Build hierarchy | Direct relationship evidence | Untested |
| Show assignment | Explain the card's work | Source-provided instruction or summary | Untested |
| Show execution status | Display source state | Documented transition evidence | Untested |
| Show terminal outcome | Mark result without guessing | Authoritative terminal evidence | Directly observed |
| Handle approval | Surface and answer attention | Bidirectional request/response evidence | Untested |
| Recover history | Rebuild continuity | Restart/reconnect evidence | Untested |
| Detect gaps | Avoid false completeness | Missing-history or cursor evidence | Untested |
| Continue in background | Avoid silent task loss | Proven public runtime lifecycle | Untested |

Each result must be one of: directly observed, safely derived, unavailable, ambiguous, or version/feature dependent.

## Go/no-go minimum

The agent task workspace is a go only if the pinned experiment supports:

- root execution identity;
- a correlatable child execution or an honest delegation-to-unknown-child fallback;
- an assignment or source summary for each displayed work unit;
- activity evidence;
- a terminal outcome or an explicit unknown state; and
- provenance for every displayed status.

Failure to meet the minimum triggers product re-scope. It does not authorize heuristic task generation.

# M0 contract research: Codex App Server 0.170.0

## Scope and evidence status

This note supports [Orbita issue #2](https://github.com/RockyRous/Orbita/issues/2). It records the public contract exposed by the exact local Codex installation and checks that contract against first-party OpenAI sources. It does **not** claim that issue #2's authenticated root-task round trip has run: this research track used contract-generation and read-only inspection only. A builder still has to capture the live, sanitized request/response/notification fixture.

Evidence priority follows [compatibility.md](compatibility.md): local binary help and generated output first, then the version-pinned official repository and official OpenAI documentation. All repository links below are pinned to the `rust-v0.170.0` release tag or its commit, not `main`.

## Reproducible inspection and generation

Run from a PowerShell prompt. These commands do not require handwritten method or payload definitions:

```powershell
Get-Command codex | Format-List Name,CommandType,Source,Path,Version
codex --version
codex --help
codex app-server --help
codex app-server generate-json-schema --help
codex app-server generate-ts --help
codex features list
npm list -g @openai/codex --depth=0
```

Generate both filtered and opt-in contract variants into a new disposable directory:

```powershell
$probeRoot = Join-Path ([System.IO.Path]::GetTempPath()) ('orbita-m0-contract-' + [guid]::NewGuid().ToString('N'))
New-Item -ItemType Directory -Path $probeRoot | Out-Null

codex app-server generate-json-schema --out (Join-Path $probeRoot 'schema-stable')
codex app-server generate-json-schema --experimental --out (Join-Path $probeRoot 'schema-experimental')
codex app-server generate-ts --out (Join-Path $probeRoot 'ts-stable')
codex app-server generate-ts --experimental --out (Join-Path $probeRoot 'ts-experimental')
```

`--out` is required for both generators. `--experimental` means “include experimental methods and fields in the generated output”; it is a generator option, not an App Server launch option. The official exporter defaults `experimental_api` to false and removes experimental request variants, fields, and type files when false ([export implementation, lines 108-150](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-protocol/src/export.rs#L108-L150), [JSON filtering, lines 216-269](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-protocol/src/export.rs#L216-L269)).

## Confirmed public surface

### Transport and connection lifecycle

`codex app-server --listen stdio://` is the minimal public launch path. `stdio://` is the default. The local help also exposes `unix://`, `unix://PATH`, `ws://IP:PORT`, and `off`; the version-pinned parser confirms that set and default ([transport parser, lines 83-168](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-transport/src/transport/mod.rs#L83-L168)). The stdio transport reads one line at a time and appends a newline to each serialized outbound message ([stdio transport, lines 66-95](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-transport/src/transport/stdio.rs#L66-L95), [lines 97-148](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-transport/src/transport/stdio.rs#L97-L148)). Therefore the probe must use newline-delimited JSON on stdin/stdout, keep stderr separate, and keep stdin open while awaiting notifications.

Initialization is once per connection. `InitializeParams` requires `clientInfo.name`, `clientInfo.version`, and a nullable title; capabilities include the explicit `experimentalApi` opt-in ([v1 protocol, lines 27-74](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-protocol/src/protocol/v1.rs#L27-L74)). The server rejects non-initialize requests before initialization with `Not initialized` ([message processor, lines 1003-1054](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server/src/message_processor.rs#L1003-L1054)). The generated client notification contract contains `initialized` after the initialize response ([protocol registration, lines 2200-2202](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-protocol/src/protocol/common.rs#L2200-L2202)). Official OpenAI guidance gives the same ordering: send `initialize`, wait for success, then send `initialized` ([Codex app-server guidance](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server)).

Closing stdio is not a terminal turn signal. It closes that transport connection and the single-client stdio server exits after connection cleanup ([runtime loop, lines 1222-1241](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server/src/lib.rs#L1222-L1241)). Orbita must never infer a completed turn from EOF, process exit, silence, or an item finishing.

### Stable-only core methods and events

The following are present in the output generated **without** `--experimental`:

- `initialize` request and `initialized` client notification;
- `thread/start` request/response and `thread/started` notification;
- `turn/start` request/response;
- `turn/started`, `item/started`, `item/completed`, streaming item deltas, `error`, and `turn/completed` server notifications.

The version-pinned registrations show `initialize` without an experimental attribute ([common protocol, lines 522-527](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-protocol/src/protocol/common.rs#L522-L527)), `thread/start` ([lines 572-580](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-protocol/src/protocol/common.rs#L572-L580)), `turn/start` ([lines 1113-1118](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-protocol/src/protocol/common.rs#L1113-L1118)), and the lifecycle notifications ([lines 2050-2057](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-protocol/src/protocol/common.rs#L2050-L2057), [lines 2082-2090](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-protocol/src/protocol/common.rs#L2082-L2090)).

“Stable-only” here means retained by this binary's non-`--experimental` contract generator. It does not erase the CLI's top-level `[experimental]` marker for App Server. It also does not make every field on a retained type stable: for example, `ThreadStartParams` has both retained fields and individually marked experimental fields ([thread types, lines 57-168](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-protocol/src/protocol/v2/thread.rs#L57-L168)). Builder code must consume the generated stable-only type, not copy the full Rust struct from source.

## Minimal source-confirmed sequence for issue #2

The examples below are newline-delimited messages. They intentionally omit `jsonrpc`: the generated `ClientRequest` contract and official examples use `method`, `id`, and `params` directly. Angle-bracket values are fixture inputs or IDs returned by the server, not literal protocol values.

1. Start the pinned process in the disposable project context:

   ```powershell
   codex app-server --listen stdio://
   ```

2. Send `initialize`, wait for the matching successful response, then send `initialized`:

   ```json
   {"method":"initialize","id":1,"params":{"clientInfo":{"name":"orbita_m0_probe","title":"Orbita M0 Probe","version":"0.0.1"},"capabilities":{"experimentalApi":false}}}
   {"method":"initialized"}
   ```

   The initialize response contains `userAgent`, `codexHome`, `platformFamily`, and `platformOs` in this version ([response type, lines 76-88](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-protocol/src/protocol/v1.rs#L76-L88)). Record it, but sanitize local paths before publishing a fixture.

3. Start one thread. Use an actual absolute disposable-project path. An explicit recorded model is preferable for the final probe; if omitted, record the resolved `result.model` and `result.modelProvider` from the response.

   ```json
   {"method":"thread/start","id":2,"params":{"cwd":"<ABSOLUTE_DISPOSABLE_PROJECT>","approvalPolicy":"never","sandbox":"read-only","ephemeral":true}}
   ```

   Wait for response `id: 2`; save `result.thread.id` as `<THREAD_ID>`. Also capture `thread/started`. The request, response, and notification types are public and source-defined ([thread start request/response, lines 57-224](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-protocol/src/protocol/v2/thread.rs#L57-L224), [notification, lines 2198-2207](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-protocol/src/protocol/v2/thread.rs#L2198-L2207)). Do not assume whether the response or notification is observed first; correlate by thread ID.

4. Start one turn with the returned thread ID:

   ```json
   {"method":"turn/start","id":3,"params":{"threadId":"<THREAD_ID>","input":[{"type":"text","text":"Reply with exactly: ORBITA_M0_OK","text_elements":[]}]}}
   ```

   Wait for response `id: 3`; save `result.turn.id` as `<TURN_ID>`. Capture `turn/started`, all matching `item/*` and delta notifications, and `turn/completed`. `threadId` and `input` are required by the generated stable type; the response returns a `Turn` ([turn start types, lines 176-321](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-protocol/src/protocol/v2/turn.rs#L176-L321)).

5. Treat only the matching `turn/completed` notification as the authoritative terminal evidence for this round trip. It carries both `threadId` and the final `turn`; `turn.status` is one of `completed`, `interrupted`, `failed`, or `inProgress` in the type, although a completed notification should be evaluated by its delivered status ([turn statuses, lines 31-39](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-protocol/src/protocol/v2/turn.rs#L31-L39), [terminal notification, lines 598-621](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-protocol/src/protocol/v2/turn.rs#L598-L621)). Official OpenAI guidance is stricter for outcome classification: on `turn/completed`, only `status: "completed"` is success; `failed` and `interrupted` are not ([Codex app-server guidance](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server)). An `error` notification has `willRetry` and is not by itself terminal; do not infer terminal state from it, from `item/completed`, or from transport closure.

This sequence proves one root thread and turn only. Follow-up, interrupt, delegation, approval, recovery, and background continuation belong to later gates and are not established by this note.

## Uncertainties and blockers

- No live authenticated `thread/start`/`turn/start` was executed in this research track. Authentication, selected model availability, actual event ordering, and the live terminal fixture remain the builder's work and are the only blockers to satisfying issue #2 itself.
- The local native executable matches the package version and selected committed generated files, but the public release provides no source-to-binary attestation checked here. Pin the executable SHA-256 in every fixture.
- Contract generation inherited the machine's effective Codex configuration because no CLI feature overrides were passed. The outputs repeated exactly on this machine, but a clean-machine reproduction must also capture the full `codex features list`, relevant config overrides, OS/architecture, and generator command line.
- The exact relative ordering of a request response and related lifecycle notification was not promised by the inspected sources. Consumers should correlate by request ID, thread ID, and turn ID and tolerate either order.
- `capabilities.experimentalApi: false` deliberately excludes experimental fields. If a later probe opts in, it needs a separate contract digest, capability result, and product classification; do not merge it into the stable-only claim.
- `ephemeral: true` minimizes local persistence for the disposable round trip, but it does not prove recovery or background continuation. A later continuity probe must use the documented persistence path appropriate to that gate.
- A repeated run cannot have byte-identical IDs, timestamps, token counts, or model text. “Equivalent observable result” should normalize those volatile fields and compare the contract class, correlation, lifecycle sequence, and terminal classification.

## Recommendations to the builder agent

1. Launch the exact executable identified above through `codex app-server --listen stdio://`; record package version, native hash, OS/architecture, complete effective feature output, config overrides, model/provider, and command line before sending work.
2. Generate stable-only JSON Schema and TypeScript bindings as part of the fixture acquisition step. Validate inbound and outbound messages against the stable-only contract. Preserve unknown variants as diagnostics rather than failing unrelated projection.
3. Implement the initialize handshake as a state gate: wait for response `id: 1`, then send `initialized`; do not queue thread work before it succeeds.
4. Use a new disposable Git repository with synthetic content, an absolute `cwd`, `sandbox: "read-only"`, and `approvalPolicy: "never"` for the minimal no-approval round trip. Keep stdout JSONL and stderr diagnostics separate.
5. Capture every line with direction and monotonic ordinal. Sanitize `codexHome`, `cwd`, other paths, prompts, output, environment-like values, and credentials before committing fixtures. Retain original request IDs and the server-provided thread/turn IDs only in the private raw capture if repository security rules require pseudonymization.
6. Resolve the root execution only from matching `turn/completed`. Map `completed` to success, `failed` to failure, and `interrupted` to interrupted; retain the unexpected/unknown case instead of guessing. Do not use EOF, silence, `error`, item completion, or the `turn/start` response as a terminal signal.
7. Repeat from a clean process and new disposable project. Compare normalized fixtures while ignoring generated IDs, timestamps, duration/token metrics, and unconstrained model prose. Require the same handshake, method classification, ID correlations, event classes, and final status semantics.
8. Keep experimental output and any future `experimentalApi: true` run in a separately named fixture set with its own digest. The top-level App Server and generator commands remain CLI-marked experimental even when a method survives stable-only filtering.
